## 0. 원격 개발 환경 구성

### 이중 SSH 홉 + Jupyter 원격 커널

- 노트북 파일은 이 저장소(작업 PC 또는 codeql-host)에 있지만, 실제 실행은 물리적으로 분리된 Jetson Orin Nano에서 이루어짐.
- 접속 경로: `작업 PC → codeql-host(10.10.237.5) → Jetson`
- Jupyter Lab을 처음엔 `--ip=0.0.0.0`으로 띄우려다가, 코드 실행이 가능한 서비스를 네트워크에 그대로 노출하는 것이라 자동 승인 필터에 의해 차단됨. **`127.0.0.1`(로컬호스트 전용) 바인딩 + SSH 포트포워딩(이중 터널)** 방식으로 변경해 해결.
- PowerShell에서 `plink.exe`로 원격 명령을 보낼 때, PowerShell 자체의 문자열 해석(`$변수`, `` `""` `` 이스케이프 불가, Windows argv의 큰따옴표 처리)과 원격 bash의 따옴표 규칙이 여러 겹으로 충돌해서 명령이 중간에 엉뚱하게 잘리는 문제를 여러 번 겪음. 해결 패턴:
  - 원격 실행할 파이썬 코드는 **base64로 인코딩**해서 전달 (`echo <b64> | base64 -d | python3`) — 따옴표 문제를 원천 차단.
  - PowerShell 바깥쪽은 **큰따옴표**, 그 안의 젯슨 원격 커맨드는 **작은따옴표**로 감싸는 조합만 안정적으로 동작. 반대(바깥 작은따옴표 + 안쪽 큰따옴표)는 Windows argv 단계에서 따옴표가 소실되어 명령이 codeql-host와 Jetson에 나뉘어 실행되는 사고로 이어짐 (예: `hostname -I`가 codeql-host에서 실행되어 엉뚱한 IP가 출력됨).

### USB 브릿지 → 이더넷 고정 IP로 전환

- 초기엔 Jetson이 codeql-host에 USB C타입으로만 연결되어 있어 `192.168.55.1`(l4tbr0 브릿지) 경로만 존재.
- 이후 Jetson에 이더넷 고정 IP(`192.168.237.8`, codeql-host의 `enp4s0`와 같은 대역)가 설정된 것을 확인, USB 케이블을 다른 용도로 빼도 되도록 주 접속 경로를 이더넷으로 전환. USB(`192.168.55.1`)는 폴백 경로로 유지.

## 1. Day 1 — PyTorch → HuggingFace

- **CC 8.7(Orin) 미지원 경고**: PyPI의 일반 torch 휠(`2.13.0+cu130`)에는 Jetson Orin의 정확한 Compute Capability(8.7)용 사전 컴파일 커널이 없음 — `torch.cuda.is_available()`, 모델 로드 시 매번 `No published PyTorch CUDA builds... support this GPU` 경고가 출력됨.
  - **원인**: aarch64 빌드 자체는 정상(잘못된 x86_64 빌드였다면 import 자체가 실패했을 것). 대신 가장 가까운 CC(8.0)용 PTX를 런타임에 JIT 컴파일해서 대체 실행.
  - **영향**: 기본 연산(matmul, 소형 LLM 생성)은 정상 동작하지만 최초 실행 시 JIT 컴파일 비용 때문에 느림 (2 tok/s → 워밍업 후 8 tok/s로 관찰).
  - **결론**: 무시해도 되는 경고. 다만 이후 Day마다 반복해서 마주치는 핵심 배경 지식이 됨.

## 2. Day 2 — KV Cache, TTFT/TPOT

- **`model.generate(..., use_cache=False)`가 무시됨**: 원래 계획은 `generate()`에 `use_cache=True/False`를 넘겨 속도 차이를 비교하는 것이었으나, 실제 측정해보니 두 경우 속도가 거의 동일(배율 0.96~1.05x). 이 transformers 버전에서 `generate()`가 이 플래그를 내부적으로 무시하는 것으로 보임.
  - **해결**: `generate()`에 의존하지 않고 `model()`을 직접 반복 호출하는 수동 루프로 "캐시 재사용 vs 매 스텝 전체 재계산"을 직접 구현. 이 방식으로는 실제로 배율이 나타남(n=30일 때 1.05x → n=150일 때 1.13x, 꾸준히 증가).
  - **추가로 겪은 일**: 배율을 더 뚜렷하게 보여주려고 n=500까지 올려서 테스트했다가, `manual_no_cache`가 점점 길어지는 시퀀스를 매 스텝 전체 재계산하면서 **프로세스가 OOM으로 강제 종료(exit 137)**됨. 8GB 통합 메모리 환경에서 시퀀스 길이 실험은 신중하게 늘려야 한다는 교훈.
- **"긴 prompt인데 TTFT가 더 짧게" 나온 역전 사례**: 콜드스타트 재현 실험(`cell-13`)에서 330토큰짜리 긴 prompt를 워밍업된 상태로 2회차 측정했더니 TTFT 95.7ms가 나왔는데, 이는 바로 앞 실험(`cell-11`)의 40토큰 prompt TTFT(118.9ms)보다 오히려 **더 짧은** 값이었음. "prompt가 길수록 TTFT가 커진다"는 이론과 표면적으로 안 맞아 보임.
  - **해석**: 0.5B급 소형 모델·수백 토큰 규모에서는 attention 연산량 자체의 증가분보다 커널 launch 같은 고정 오버헤드나 측정 시점의 시스템 노이즈(Jetson은 자원을 공유하는 엣지 기기라 흔들림이 상대적으로 큼) 비중이 더 커서, 서로 다른 실행(별개 함수 호출) 간 단순 비교로는 이 역전이 나타날 수 있음.
  - **교훈**: prompt 길이 vs TTFT의 정비례 관계를 검증하려면, **같은 프로세스·같은 워밍업 상태에서 길이만 바꿔가며 연속 비교**해야 신뢰할 수 있다 (`cell-16`처럼 짧은/중간/긴 prompt를 한 루프 안에서 순서대로 측정). 서로 다른 시점에 측정된 값끼리 절대 비교하는 건 이런 노이즈에 취약하다.

## 3. Day 3 — FastAPI 추론 서버 + 배칭

- **커널과 파일이 서로 다른 머신에 있다는 구조적 문제**: 노트북 커널은 Jetson에서 실행되는데 저장소 파일(및 `%%writefile ../serving/server.py` 같은 상대경로)은 작업 PC/codeql-host에 있음. `%%writefile ../serving/server.py`를 그대로 쓰면 Jetson 쪽 엉뚱한 위치에 파일이 생성됨.
  - **해결**: Jetson 쪽 절대경로(`~/jetson_mlops_serving`)에 파일을 쓰도록 변경하고, 완성된 코드를 저장소의 `serving/server.py`로 수동 복사하는 절차를 명시.
- **실측 결과가 기대보다 좋았던 사례**: 배칭 유무 처리량 비교에서 애초 예상은 "1.3~2배" 정도였는데, 실제로는 **4.09배** 향상 (배칭 없음 0.32 req/s → 있음 1.32 req/s). 작은 모델(0.5B)일수록 GPU 커널 launch 고정 오버헤드 비중이 커서, 배칭으로 그 오버헤드를 나눠 갚는 효과가 예상보다 크게 나타난 것으로 추정.

## 4. Day 4 — 양자화 (가장 큰 사고가 난 Day)

### 4-1. bitsandbytes: 토이 테스트는 성공, 실제 모델은 실패

- 64×64 랜덤 텐서로 `Linear8bitLt`를 테스트하면 에러 없이 통과 → "동작하네?" 싶었지만, **실제 모델을 `BitsAndBytesConfig(load_in_8bit=True)`로 로드해서 `generate()`를 호출하면 `cuBLAS API failed with status 15`로 실패**.
- **교훈**: 작은 토이 예제로 라이브러리 동작 여부를 판단하는 건 신뢰할 수 없다. 실제 모델의 실제 연산 크기/shape에서만 드러나는 실패가 있음.

### 4-2. optimum-quanto int4: 컴파일이 기기를 통째로 멈춤 (심각)

1차 시도: `RuntimeError: Ninja is required to load C++ extensions` — int4(AWQ 커널) 경로는 최초 실행 시 CUDA 커널을 즉석 JIT 컴파일하는데 `ninja`가 없어서 실패.

`pip install ninja` 후 재시도했더니 컴파일은 시작됐지만, **AWQ/Marlin/GPTQ 등 CUDA 확장 라이브러리 전체를 한꺼번에 병렬로(cudafe++/cc1plus 프로세스 5~6개) 컴파일**하면서 각 프로세스가 1GB 이상 메모리를 사용, **8GB 통합 메모리 + 2GB 스왑을 전부 소진**시킴. 결과:

- `free -h` 기준 RAM 7.4Gi/7.4Gi, Swap 2.0Gi/2.0Gi 전부 사용
- load average 19.68 (평상시 대비 극단적으로 높음)
- **SSH 접속 자체가 몇 분간 안 되는 상태**로 기기 전체가 멈춤

`ping`은 응답했지만 SSH 배너 교환이 타임아웃되는 상태가 지속됨. `Monitor` 도구로 SSH 복구를 기다린 뒤, 살아남은 `cudafe++`/`cc1plus` 프로세스들을 `pkill`로 강제 종료해서 복구.

- **교훈**: 8GB급 통합 메모리 엣지 기기에서 "필요할 때 CUDA 커널을 즉석 컴파일"하는 라이브러리는 컴파일 자체가 무거운 리소스 소비 작업이라는 걸 잊기 쉽다. 데스크탑/서버(RAM 32GB+)에서는 무해한 일이 엣지 기기에서는 시스템 전체를 멈추는 사고로 이어질 수 있다.
- **최종 결정**: 이 노트북에서는 int4 quanto를 실행 셀에서 제외하고, 실제로 겪은 위험을 경고 markdown으로 남김. int4가 필요하면 사전 양자화된 GGUF + llama.cpp(컴파일 없이 가중치만 다운로드) 경로를 권장.

### 4-3. 그 외

- `apply_chat_template(..., return_tensors="pt")`를 바로 쓰면 `.shape` 접근 시 `AttributeError` 발생 — `tokenize=False`로 문자열만 받고 별도로 `tokenizer(text, return_tensors="pt")` 하는 패턴으로 전부 통일.
- `optimum-quanto` int8은 문제없이 GPU에서 동작 (메모리 0.72GB, fp16의 ~1GB보다 소폭 감소).

## 6. Day 6 — 평가 · 모니터링

- **venv의 콘솔 스크립트가 PATH에 안 잡히는 문제**: `~/mlops-lab-env/bin/python3`를 직접 호출하는 방식(activate 스크립트 미실행)에서는 `PATH`에 venv의 `bin`이 없어서, `ninja`처럼 PATH 룩업이 필요한 도구를 못 찾는 문제가 있었음 (Day4의 원인이기도 함). `os.environ["PATH"]`에 직접 추가해서 해결 가능.

- `tegrastats` 정규식(`RAM`, `GR3D_FREQ`, `tj@`/`gpu@` 온도)은 실제 출력과 대조해 정상 동작 확인.

## 7. 추가 트랙 — 비전 모델 경량화 (torchvision 양자화 + TensorRT)

LLM 스프린트와 별개로 ResNet-18을 대상으로 경량화 실습 노트북(`vision_compression_practice.ipynb`)을 만들며 겪은 것.

### 7-1. torchvision 설치 — torch를 덮어쓸 뻔함

- `pip install torchvision`을 그냥 하면 의존성 해결 과정에서 특수 빌드된 `torch 2.13.0+cu130`(Jetson CUDA 빌드)을 일반 빌드로 교체하려 할 위험이 있음.
- **`pip install --no-deps torchvision`** 으로 0.28.0만 설치 → torch 안 건드리고 CUDA 정상 동작(fp32 forward 확인).

### 7-2. 양자화 백엔드: aarch64에서 `unknown architecture`

- 이 torch 빌드의 기본 양자화 엔진이 `x86`이라, Jetson(aarch64)에서 quantized conv를 prepack할 때 `RuntimeError: unknown architecure`로 실패.
- 확인 결과 지원 엔진은 `['qnnpack','onednn','x86','fbgemm']`인데 **x86/fbgemm은 실패, qnnpack/onednn은 성공**. ARM용 `qnnpack`을 `torch.backends.quantized.engine = "qnnpack"`으로 명시해야 함.
- torchvision `resnet18(quantize=True)`의 내부 백엔드 자동선택도 x86으로 잡혀 실패 → quantizable 아키텍처에 표준 float 가중치를 `strict=False`로 얹고 **수동 PTQ(fuse → qconfig(qnnpack) → prepare → calibrate → convert)** 로 우회.

### 7-3. 핵심 관찰: CPU INT8은 작지만 느리다

실측(batch=16):
```
FP32 CPU:  734.1 ms   size 44.6 MB
INT8 CPU:  905.7 ms   size 10.7 MB   <- 크기 4.2배↓ 이지만 속도는 오히려 느림
```
- 양자화 = 자동 속도향상이 아님. Cortex-A78AE에서 qnnpack INT8 커널이 이 조합에선 이득을 못 냄. 게다가 torchvision 양자화 모델은 **CPU 전용**이라 Jetson GPU를 못 씀.
- → 엣지 속도 향상의 정답은 CPU 양자화가 아니라 **GPU + TensorRT**.

### 7-4. TensorRT(trtexec)는 압도적

- TensorRT는 JetPack에 기본 포함(`/usr/bin/trtexec`), 파이썬 바인딩 불필요. `PyTorch → ONNX → trtexec 엔진 빌드+벤치` 흐름.
- 실측 GPU Compute Time(batch=16): **PyTorch eager 56ms → TRT FP32 27.8 → FP16 10.6 → INT8 5.4ms** (INT8은 eager 대비 ~10.3배, 엔진 크기 46.9→12.0MB).
- 주의: trtexec `--int8`만 주면 자동 dynamic range라 **속도 측정용**. 정확도 지키려면 캘리브레이션 캐시 필요.

### 7-5. 그 외 자잘한 것들

- torch 2.13 ONNX export는 `onnxscript` 필요(설치). 그리고 가중치를 **외부 데이터 파일(`*.onnx.data`)로 분리 저장**하므로 `.onnx`와 `.onnx.data`가 같은 폴더에 함께 있어야 trtexec가 읽음.
- **PowerShell→plink에서 `$?`는 쓰지 말 것** — PowerShell이 자체 `$?`(True/False)로 확장해 원격에 `echo TRTEXIT=True`처럼 잘못 전달됨. 또 `\"a|b\"` 형태 grep 패턴도 PowerShell 파서가 깨뜨려서, 원격에서 grep 대신 **로그 파일 저장 후 `tail`로 읽는 방식**이 안전했음.

## 종합 교훈

1. **작은 토이 예제 통과 ≠ 실제 워크로드 동작 보장** (bitsandbytes 사례).
2. **즉석 컴파일이 필요한 라이브러리는 엣지 기기에서 리소스 폭발 위험이 있다** — 실행 전에 반드시 메모리 여유를 확인하고, 가능하면 사전 컴파일/사전 양자화된 산출물을 쓰는 경로를 우선 고려할 것.
3. **콜드스타트(JIT 컴파일) 비용은 항상 첫 실행에 몰린다** — 벤치마크/측정 코드에는 워밍업이 선택이 아니라 필수.
4. **버전마다 API 동작이 다를 수 있다** (`use_cache=False` 무시, `apply_chat_template` 반환 타입) — 문서/기억에 의존하지 말고 실제로 돌려서 확인.
5. **원격 실행 환경(커널 위치 ≠ 파일 위치)에서는 상대경로가 위험하다** — 항상 어느 머신 기준의 경로인지 명시적으로 구분할 것.
